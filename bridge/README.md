# สะพานแชท TikTok → คิวขอเพลง

พิมพ์ `!เพลง แสงสุดท้าย` ในแชทไลฟ์ TikTok แล้วเพลงเด้งเข้าคิวของช่องเลย
โดยคนดูไม่ต้องเปิดลิงก์อะไรทั้งนั้น

โฟลเดอร์นี้เป็นของเสริม **ไม่รันก็ใช้ระบบขอเพลงผ่านหน้าเว็บได้ตามปกติ**

มีสองแบบ ใช้ตัวเดียวกันข้างใน (`core.mjs`)

| แบบ | สำหรับ | ตั้งค่ายังไง |
| --- | --- | --- |
| **โปรแกรม** `kiew-bridge.exe` (`app.mjs`) | สตรีมเมอร์ทั่วไป | วางรหัสเชื่อมต่อจากสตูดิโอในหน้าเว็บของโปรแกรม ไม่ต้องลง Node |
| **คำสั่ง** `tiktok-song-bridge.mjs` | เจ้าของระบบ / คนถนัด | ไฟล์ `.env` ใช้ `INGEST_TOKEN` กลาง (เขียนได้ทุกช่อง) |

---

## โปรแกรมสำหรับสตรีมเมอร์ (`kiew-bridge.exe`)

สตรีมเมอร์ทำเองได้ทั้งหมดจากหน้า **สตูดิโอ → ลิงก์สำหรับ OBS** หัวข้อ “รับคำขอเพลงจากแชท TikTok”:
ดาวน์โหลด → เปิด → วางรหัสเชื่อมต่อ → เปิดค้างไว้ตอนไลฟ์

- หน้าตั้งค่า/สถานะอยู่ในเบราว์เซอร์ที่ `http://127.0.0.1:47821` (ฟังแค่เครื่องตัวเอง)
- ค่าที่ตั้งเก็บที่ `%APPDATA%\kiew-bridge\config.json`
- ติ๊ก “เปิดเองตอนเปิดเครื่อง” = ใส่ชื่อไว้ใน `HKCU\...\CurrentVersion\Run` (ไม่ต้องใช้ admin)
- เปิดซ้ำตอนที่เปิดอยู่แล้ว = แค่เปิดหน้าเว็บของตัวเดิม ไม่ฟังแชทซ้อน

**รหัสเชื่อมต่อ** ผูกกับช่องเดียว — Worker ยอมให้เขียนเฉพาะช่องที่ออกรหัสให้ (ต่างจาก `INGEST_TOKEN`
ที่เขียนได้ทุกช่อง) จึงแจกให้สตรีมเมอร์ได้ ถ้ารหัสหลุด เจ้าของช่องกด “สร้างรหัสใหม่” ในสตูดิโอ
รหัสเก่าใช้ไม่ได้ทันที — รายละเอียดฝั่ง Worker ดู `?pair=1` ใน [../worker/README.md](../worker/README.md)

### สร้างและออกรุ่นใหม่

```bash
cd bridge
npm install
npm run app          # ลองแบบไม่ build (node app.mjs)
npm run build:exe    # → dist/kiew-bridge.exe และ dist/kiew-bridge-windows.zip
```

ออกรุ่นให้สตรีมเมอร์ดาวน์โหลด: แก้ `version` ใน `package.json` แล้ว push tag ที่ตรงกัน
GitHub Actions (`.github/workflows/bridge-release.yml`) build บน Windows แล้วแนบขึ้น Releases ให้เอง
ลิงก์ในสตูดิโอชี้ `releases/latest` จึงได้รุ่นใหม่ทันที

```bash
git tag bridge-v1.0.0
git push origin bridge-v1.0.0
```

โปรแกรมไม่ได้เซ็นด้วยใบรับรอง Windows จึงขึ้น SmartScreen ตอนเปิดครั้งแรก (More info → Run anyway)
และ build ขึ้น `warning: The signature seems corrupted!` — ปกติ เพราะฝังโค้ดลงใน node.exe
ที่ Node เซ็นไว้ ลายเซ็นเดิมจึงไม่ตรงอีก

## ทำไมต้องรันบนเครื่องตัวเอง

TikTok ไม่มี API สาธารณะให้อ่านคอมเมนต์ในไลฟ์ — ที่มีในเอกสารนักพัฒนาคือ
เรื่องโพสต์กับโปรไฟล์ ไม่มีแชท ทางเดียวที่อ่านได้จริงคือต่อ WebSocket ภายใน
ของ TikTok ซึ่งต้องมีลายเซ็นจากบริการภายนอก และต้องเปิดค้างตลอดเวลาที่ไลฟ์อยู่

สองข้อนี้ทำในเว็บ static ไม่ได้ (เบราว์เซอร์โดน CORS บล็อกและเซ็นไม่ได้)
และทำใน Cloudflare Worker ธรรมดาก็ไม่ได้ เพราะ Worker ตายทันทีที่ตอบคำขอเสร็จ
มันไม่ใช่โปรแกรมที่เปิดค้างได้

เครื่องที่เปิดอยู่แล้วตอนไลฟ์ก็คือเครื่องของคนไลฟ์ — เลยเอามาไว้ตรงนี้

```
แชท TikTok ──▶ สะพาน (เครื่องเรา) ──▶ Worker ──▶ Firestore ──▶ คิว + widget เด้งเอง
                  ฟังอย่างเดียว        ตรวจ+เขียน
```

สะพานทำแค่ฟังแชทกับส่งต่อ **การตัดสินใจทั้งหมดอยู่ที่ Worker**
(ช่องเปิดรับอยู่ไหม คิวเต็มยัง คนนี้ขอเกินโควตาหรือยัง) เพราะสคริปต์ที่รัน
บนเครื่องผู้ใช้แก้ได้ ใครก็เขียนตัวเลียนแบบยิงเข้ามาได้

## ต้องมีอะไรก่อน

1. **Node.js 18 ขึ้นไป** — `node -v` เช็คได้
2. **Worker deploy แล้ว** พร้อมบัญชีบอท (`BOT_EMAIL` / `BOT_PASSWORD` /
   `FIREBASE_API_KEY` / `FIREBASE_PROJECT`) — ตัวเดียวกับที่ใช้อนุมัติสลิป
   ดู [../worker/README.md](../worker/README.md)
3. **uid ของบอทอยู่ในหน้า ช่อง → ผู้ดูแลระบบ** แล้ว
4. **publish `firestore.rules` ตัวล่าสุด** ที่ Firebase Console
   (ตัวเก่าไม่ยอมให้บอทเขียนใบแทนคนดู)
5. **คีย์ YouTube ใน Worker** ถ้าอยากให้คนดูพิมพ์ *ชื่อเพลง* ได้
   ไม่มีคีย์ก็ยังใช้ได้ แต่ต้องวางลิงก์ YouTube มาเท่านั้น

## ตั้งค่า

```bash
cd bridge
npm install
cp .env.example .env
```

สุ่ม token ขึ้นมาหนึ่งอัน

```bash
node -e "console.log(crypto.randomUUID().replace(/-/g,''))"
```

เอาค่าที่ได้ใส่ **ทั้งสองที่ให้ตรงกัน**

```bash
# ฝั่ง Worker (รันในโฟลเดอร์ worker/)
wrangler secret put INGEST_TOKEN
wrangler deploy
```

```ini
# ฝั่งสะพาน — ไฟล์ bridge/.env
TIKTOK_USER=ชื่อ_tiktok_ที่ไลฟ์
WORKER_URL=https://slip-verify.xxxx.workers.dev
INGEST_TOKEN=ค่าที่สุ่มมา
CHANNEL=handle_ของช่อง
```

`CHANNEL` ใส่ handle ได้เลย — คือตัวที่อยู่ท้ายลิงก์หน้าขอเพลง
(`.../song/#h=affarain` → ใส่ `affarain`) หรือจะใส่ไอดีเอกสารของช่องก็ได้

แล้วเปิดหน้าจัดการช่องดูได้เลย ใบจะอยู่ในคิวพร้อมป้าย **TikTok**
(ลบทิ้งได้ตามปกติ)

## เปิดทิ้งไว้ตลอด ไม่ต้องมีคนนั่งเฝ้า (Windows)

ดับเบิลคลิก `run-forever.cmd` — สะพานจะรันอยู่ในหน้าต่างนั้น ล้มเมื่อไหร่เปิดใหม่เอง
ในหนึ่งนาที ช่วงไม่ได้ไลฟ์มันรอเงียบๆ แล้วต่อเองเมื่อเริ่มไลฟ์ จบไลฟ์ก็กลับไปรอรอบถัดไป

- ข้อความทั้งหมดไปอยู่ที่ `logs/bridge.log` (หน้าต่างจะว่าง) ดูสดๆ ได้ด้วย
  `powershell Get-Content logs\bridge.log -Wait -Tail 20`
- ปิดหน้าต่าง = หยุดสะพาน
- **เปิดเองตอนเปิดเครื่อง** — กด `Win+R` พิมพ์ `shell:startup` แล้ววางทางลัดของ
  `run-forever.cmd` ไว้ในโฟลเดอร์นั้น (ตั้ง Run เป็น Minimized จะได้ไม่บังจอ)
  มันเริ่มตอน **ล็อกอิน Windows** ถ้าเครื่องรีสตาร์ตเอง (Windows Update) ต้องมีคนล็อกอินก่อน
- เครื่องต้องไม่ sleep — Settings → System → Power → Sleep = Never

ช่องเดียวกันเปิดได้ทีละตัว: ถ้า `run-forever.cmd` รันอยู่แล้วมีคนพิมพ์ `npm start` ซ้ำ ตัวหลังจะหยุดเองพร้อมบอกเหตุ
(สองตัวฟังไลฟ์เดียวกัน = ทุกคำขอเข้าคิวสองรอบ) ตัวจองอยู่ที่ไฟล์ `.bridge-<ช่อง>.lock`

### หลายช่องบนเครื่องเดียว

แยกไฟล์ตั้งค่าละช่อง ตั้งชื่อลงท้าย `.env` (gitignore ไว้แล้ว) แล้วบอกชื่อไฟล์ตอนรัน

```bat
copy .env bammmmyyi.env          :: แก้ TIKTOK_USER กับ CHANNEL ในไฟล์ใหม่
node tiktok-song-bridge.mjs --env bammmmyyi.env
run-forever.cmd bammmmyyi.env    :: log ไปที่ logs\bridge-bammmmyyi.log
```

ทางลัดใน `shell:startup` ก็ใส่ชื่อไฟล์ในช่อง Target ต่อท้าย `run-forever.cmd` แบบเดียวกัน

## เรื่องโควตา YouTube (ข้อจำกัดที่สำคัญที่สุด)

โควตาฟรีของ YouTube Data API คือ 10,000 หน่วย/วัน และการค้นหาครั้งละ 100 หน่วย
= **ค้นได้ราววันละ 100 ครั้ง** ซึ่งไลฟ์ที่คนดูคึกๆ หมดได้ใน 20 นาที

ตัวช่วยที่ใส่ไว้แล้ว

- **แคชผลค้นหา** ฝั่ง Worker — คนขอเพลงฮิตซ้ำๆ กันจะไม่กินโควตาซ้ำ
  (ผูก KV ชื่อ `SONG_CACHE` เพิ่มจะข้ามการรีสตาร์ทได้ด้วย ดู `worker/wrangler.toml`)
- **หน่วงรายคน** `COOLDOWN_SEC` — ค่าเริ่มต้น 45 วินาที
- **เพดานต่อช่อง/ต่อคนต่อนาที** ฝั่ง Worker

ถ้ายังไม่พอ ทางที่ได้ผลที่สุดคือประกาศในไลฟ์ให้วาง **ลิงก์** แทนชื่อเพลง
เพราะลิงก์ใช้ oEmbed ซึ่งไม่มีโควตาเลย

## เรื่องโควตาต่อแชท (Euler Stream)

ทุกครั้งที่สะพานต่อเข้าไลฟ์ ไลบรารีต้องขอลายเซ็นจาก Euler Stream หนึ่งครั้ง
ไม่ใส่ `SIGN_API_KEY` = โควตาฟรีต่อ IP **5 ครั้ง/นาที 30 ครั้ง/ชั่วโมง 100 ครั้ง/วัน**
สะพานทุกตัวที่ออกเน็ตเดียวกันใช้ก้อนเดียวกัน (ตอนต่อติดแล้วอ่านแชทยาวๆ ไม่กินเพิ่ม)

สะพานคุมเองไม่ให้ใช้เกิน (ตั้งแต่ 1.0.2)

- ถามยอดคงเหลือก่อนต่อทุกครั้ง (ถามฟรี) และนับเองในโปรแกรมอีกชั้น — หมดแล้ว **หยุดรอ** ถึงเวลารีเซ็ต
  ขึ้นว่า `พักการต่อ — โควตาบริการเชื่อมต่อแชท... เต็ม · ลองใหม่ HH:MM น.`
- รอไลฟ์เริ่มไม่กินโควตา (ถาม TikTok ตรง) ทุก 1 นาที ผ่านไป 10 นาทีเป็นทุก 2 นาที
- ไลฟ์จบแล้วรอ 1 นาทีก่อนเช็คใหม่ — TikTok มักบอกว่าห้องเดิมยังไลฟ์อยู่อีกพัก
  ต่อติดแล้วหลุดทันทีซ้ำๆ จะถอยเป็น 2 → 4 → 8 → 15 นาที (เคยวนนาทีละ 5 รอบจนโควตาหมด)
- โดนปฏิเสธ (429) พัก 2 → 5 → 15 → 30 → 60 นาที ไม่ยิงซ้ำทุก 5 วิแบบเดิม

## ข้อควรรู้

**ไลบรารีนี้ไม่ใช่ของทางการ** `tiktok-live-connector` เป็นการถอดรหัสโปรโตคอล
ภายในของ TikTok เอง เวลา TikTok เปลี่ยนของ มันจะพังจนกว่าไลบรารีจะอัปเดตตาม
(`npm update` แล้วลองใหม่) การอ่านแชทเฉยๆ ไม่ใช่สิ่งที่ TikTok ไล่แบน
แต่ก็ไม่มีอะไรรับประกัน — อย่าเอาไปผูกกับอะไรที่ขาดไม่ได้

**สะพานตอบกลับในแชท TikTok ไม่ได้** เพราะการพิมพ์ต้องใช้บัญชีที่ล็อกอินอยู่
ซึ่งเป็นคนละเรื่องกับการอ่าน คนดูจะรู้ว่าเพลงเข้าคิวแล้วจาก widget บนจอไลฟ์
หรือจากที่สตรีมเมอร์พูดเอง

**ทางเลือกที่ไม่ต้องรันสะพาน** ถ้าใช้ TikFinity หรือ Social Stream Ninja อยู่แล้ว
ตั้งให้มันยิง webhook มาที่ `POST <WORKER_URL>/?ingest=1` ได้เลย
ใส่ header `Authorization: Bearer <INGEST_TOKEN>` แล้วส่ง JSON

```json
{ "channelId": "handle", "user": { "id": "someone", "name": "Someone" }, "text": "!เพลง ชื่อเพลง" }
```

ใช้ `text` (บรรทัดแชทดิบ) แทน `query` ได้ — Worker จะตัดคำสั่งให้เอง
