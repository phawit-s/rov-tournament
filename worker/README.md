# ตัวกลางตรวจสลิป (Cloudflare Worker)

โฟลเดอร์นี้เป็นของเสริม **ไม่ deploy ก็ใช้เว็บได้ตามปกติ** ข้ามไปอ่านหัวข้อ
[ไม่อยาก deploy ได้ไหม](#ไม่อยาก-deploy-ได้ไหม) ได้เลยถ้าไม่สนใจ

Worker ตัวเดียวนี้รับงานทุกอย่างที่ต้องมีเซิร์ฟเวอร์ แยกตามพารามิเตอร์ใน URL
— ตรวจสลิป (`POST /`) · ค้นเพลง (`?search=`) · [รับคำขอเพลงจากแชทไลฟ์](#รับคำขอเพลงจากแชทไลฟ์-ingest1) (`?ingest=1`)

---

## ทำไมต้องมีตัวกลาง

เว็บนี้เป็น **static export** คือมีแต่ไฟล์ HTML/JS วางบน GitHub Pages
ไม่มีเซิร์ฟเวอร์ของตัวเอง ซึ่งเป็นข้อดี (ฟรี เร็ว ไม่ต้องดูแล) แต่แลกมาด้วยสองข้อจำกัด

**1. ใส่ API key ในหน้าเว็บไม่ได้**
อะไรที่อยู่ในหน้าเว็บ ผู้ใช้เปิด DevTools ก็อ่านได้หมด ใครก็ก๊อปคีย์เราไปยิง
จนโควตาหมด แล้วบิลมาถึงเรา

**2. ผู้ให้บริการตรวจสลิปไม่เปิด CORS**
ต่อให้ยอมเสี่ยงใส่คีย์ลงไป เบราว์เซอร์ก็จะบล็อกคำขอตั้งแต่แรกอยู่ดี
เพราะ API พวกนี้ออกแบบมาให้เรียกจากเซิร์ฟเวอร์เท่านั้น

Worker ตัวนี้เลยทำหน้าที่คนกลางตัวเล็กๆ

```
เบราว์เซอร์ ──(payload จาก QR บนสลิป)──▶ Worker ของเรา ──(+ API key)──▶ ผู้ให้บริการ
     ◀────────(ผลตรวจรูปแบบเดียว)────────      ◀──────(ผลดิบของแต่ละเจ้า)──────
```

คีย์อยู่ในตัว Worker ฝั่งเซิร์ฟเวอร์ ไม่เคยหลุดไปถึงเบราว์เซอร์
และ Worker ยัง **ตรวจซ้ำเองอีกรอบ** ว่ายอดกับเลขบัญชีปลายทางตรงไหม
เพราะใครก็ยิง POST มาที่ Worker เองได้ จะเชื่อค่าที่เบราว์เซอร์ส่งมาอย่างเดียวไม่ได้

Cloudflare Workers มีแพ็กเกจฟรี 100,000 คำขอ/วัน ซึ่งเหลือเฟือสำหรับงานนี้
ค่าใช้จ่ายจริงจึงอยู่ที่ฝั่งผู้ให้บริการตรวจสลิปอย่างเดียว

## เลือกผู้ให้บริการ

ราคาที่รวบรวมไว้ ณ **ก.ค. 2026** — ผู้ให้บริการเปลี่ยนแพ็กเกจกันบ่อย
**ควรเปิดหน้าเว็บของแต่ละเจ้าเช็คอีกครั้งก่อนสมัคร**

| เจ้า | ค่า `PROVIDER` | ฟรี | เริ่มต้น | เหมาะกับ |
| --- | --- | --- | --- | --- |
| Thunder | `thunder` | 150 สลิป/เดือน | 99 บาท / 400 สลิป | ทัวร์นาเมนต์ทั่วไป เริ่มลองฟรีได้เลย |
| SlipOK | `slipok` | — | 210 บาท / 500 สลิป | ต้องตั้ง `BRANCH_ID` เพิ่ม |
| EasySlip | `easyslip` | — | 350 บาท / 1,000 สลิป | ยอดใช้งานเยอะ ต่อสลิปถูกสุด |

คิดเป็นราคาต่อสลิป: Thunder ~0.25 บาท · SlipOK ~0.42 บาท · EasySlip ~0.35 บาท

> adapter ของ Thunder อ้างอิงเอกสาร `POST https://api.thunder.in.th/v2/verify/bank`
> (ตรวจกับ [เอกสารทางการ](https://document.thunder.in.th/en/examples/javascript) แล้ว)
> ส่วนของ SlipOK กับ EasySlip เขียนจากข้อมูลที่รวบรวมมา **ยังไม่ได้ยิงจริง**
> ถ้าจะใช้สองเจ้านั้น เปิดเอกสารของเขาเทียบ endpoint กับชื่อฟิลด์อีกรอบก่อน

**แนะนำให้เริ่มจาก Thunder** เพราะมีโควตาฟรีให้ลองว่าระบบเข้ากันได้ไหม
ก่อนตัดสินใจจ่าย ถ้าโดเนทเยอะจนเกิน 150 ใบ/เดือนค่อยย้าย
(ย้ายง่ายมาก แก้ `PROVIDER` ใน `wrangler.toml` กับใส่คีย์ใหม่ แล้ว deploy อีกรอบ)

## ขั้นตอน deploy

ต้องมี Node.js กับบัญชี Cloudflare (สมัครฟรี) ก่อน

```bash
# 1. ติดตั้งเครื่องมือ
npm i -g wrangler

# 2. ล็อกอิน (จะเปิดเบราว์เซอร์ให้กดอนุญาต)
wrangler login

# 3. เข้ามาในโฟลเดอร์นี้
cd worker

# 4. ตั้งค่า PROVIDER และ ALLOWED_ORIGIN ใน wrangler.toml ก่อน (สำคัญ ดูหัวข้อถัดไป)

# 5. ใส่ API key ของผู้ให้บริการ — เก็บเป็น secret ไม่ใช่ในไฟล์
wrangler secret put API_KEY

# 6. ขึ้นจริง
wrangler deploy
```

เสร็จแล้วจะได้ URL หน้าตาประมาณ

```
https://slip-verify.<ชื่อบัญชีเรา>.workers.dev
```

**เอา URL นั้นไปวางในเว็บ** ที่หน้า **ช่อง → ตรวจสลิปอัตโนมัติ**
แล้วกดบันทึก ถ้าอยากให้ระบบอนุมัติใบที่ตรวจผ่านให้เองโดยไม่ต้องกด
ให้เปิดสวิตช์อนุมัติอัตโนมัติในหน้าเดียวกัน

ทดสอบเร็วๆ ว่า Worker ตื่นอยู่ไหม

```bash
curl -X POST https://slip-verify.xxx.workers.dev \
  -H "Content-Type: application/json" \
  -d '{"payload":"ทดสอบ"}'
```

ควรได้ JSON กลับมาเสมอ (ต่อให้ตรวจไม่ผ่านก็ตอบ `{"ok":false,"reason":"..."}`
Worker ตัวนี้ไม่คืน error 500 เปล่าๆ โดยตั้งใจ เว็บจะได้ไม่พังตาม)

## ห้ามลืม: ล็อก `ALLOWED_ORIGIN`

`wrangler.toml` ในโฟลเดอร์นี้ใส่โดเมนของเว็บนี้ไว้ให้แล้ว
ถ้า fork ไปใช้เองอย่าลืมแก้เป็นโดเมนตัวเอง และ**ห้ามใส่ `"*"`**
เพราะนั่นแปลว่าเว็บไหนก็เรียก Worker ของเราได้ ใครรู้ URL ก็เอาไปตรวจสลิปของตัวเองฟรี
โดยหักโควตาที่เราจ่าย

```toml
[vars]
ALLOWED_ORIGIN = "https://myname.github.io"
```

ใส่เป็น origin เต็ม ไม่ต้องมี `/` ปิดท้าย แล้ว `wrangler deploy` ใหม่
ตั้ง `MAX_PER_MIN` ไว้ด้วยจะช่วยกันคนยิงรัวๆ ได้อีกชั้น

## ไม่อยาก deploy ได้ไหม

**ได้ และระบบก็ยังกันโกงให้อยู่**

เว็บอ่าน QR บนสลิปเองในเบราว์เซอร์ ทำ SHA-256 เป็น "ลายนิ้วมือ" ของสลิปใบนั้น
แล้วจดไว้ในฐานข้อมูล กติกาฝั่งฐานข้อมูลตั้งไว้ว่าลายนิ้วมือเดิม **เขียนทับไม่ได้**
สลิปใบหนึ่งจึงส่งได้ครั้งเดียวตลอดกาล

นี่กันการโกงที่เจอบ่อยที่สุดได้แล้ว — เอาสลิปเก่าของตัวเองส่งซ้ำ
หรือเอาสลิปที่คนอื่นโพสต์ไว้มาใช้ ทั้งหมดนี้ทำงานฟรี ไม่ต้องมีเซิร์ฟเวอร์

สิ่งที่ **ไม่ได้** ถ้าไม่มี Worker คือการยืนยันกับธนาคารว่าเงินเข้าจริงและยอดตรง
ใบที่อ่าน QR ได้แต่ยังไม่ได้ยืนยันจะขึ้นสถานะ `unique` ให้ผู้จัดกดตรวจเอง
ส่วนใบที่เป็นภาพแคปหน้าจอ (ไม่มี QR) จะขึ้น `none` แปลว่าต้องดูด้วยตา

สรุปสั้นๆ: **ไม่มี Worker = กันสลิปซ้ำ · มี Worker = กันสลิปซ้ำ + ยืนยันเงินเข้าจริง**

## รูปแบบข้อมูลที่รับส่ง

**คำขอ** `POST` JSON

| ฟิลด์ | จำเป็น | ความหมาย |
| --- | --- | --- |
| `payload` | ✓ | สตริงดิบที่อ่านได้จาก QR บนสลิป |
| `expectAmount` | | ยอดที่ผู้โอนแจ้งไว้ (บาท) ใส่มาแล้ว Worker จะเทียบให้ |
| `expectAccount` | | เลขบัญชี/พร้อมเพย์ปลายทางของเรา เทียบเฉพาะ 4 หลักท้าย |
| `channelId` + `donationId` | | ใบที่จะให้อนุมัติถ้าตรวจผ่าน (ต้องตั้งบัญชีบอทไว้ก่อน) |

> สองฟิลด์ `expect*` มาจากเบราว์เซอร์ จึงเป็นได้แค่ตัวกรองชั้นแรกไว้ตอบคนโอนเร็วๆ
> ตอนจะ**อนุมัติจริง** Worker ไม่เชื่อค่าพวกนี้ — มันอ่านยอดจากใบและอ่านเลขพร้อมเพย์
> จากเอกสารช่องใน Firestore มาเทียบเอง (ดูหัวข้อถัดไป)

**คำตอบ** status 200 เสมอ

```json
{
  "ok": true,
  "amount": 100,
  "at": "2026-07-29T03:20:30.000Z",
  "bank": "KBANK",
  "receiver": "นาย ก",
  "approved": true,
  "approveNote": "approved",
  "raw": { }
}
```

`raw` คือผลดิบของผู้ให้บริการ เก็บไว้เผื่อต้องดูย้อนหลัง
`approved` บอกว่า Worker พลิกใบเป็น approved ให้แล้วหรือยัง ส่วน `approveNote` บอกเหตุผลถ้าไม่ได้ทำ
ถ้า `ok` เป็น `false` จะมี `reason` มาด้วย

| `reason` | แปลว่า |
| --- | --- |
| `amount-mismatch` | ยอดในสลิปต่างจากที่แจ้งเกิน 1 บาท |
| `account-mismatch` | เลขบัญชีปลายทางไม่ใช่ของเรา |
| `slip-not-found` | ผู้ให้บริการไม่รู้จักสลิปใบนี้ (อาจปลอมหรือเก่าเกินไป) |
| `no-payload` | ไม่ได้ส่ง `payload` มา |
| `no-amount` | อ่านยอดจากคำตอบไม่ได้ ต้องตรวจด้วยตา |
| `unknown-provider` / `not-configured` / `missing-branch-id` | ตั้งค่า Worker ไม่ครบ |
| `rate-limited` | ยิงถี่เกิน `MAX_PER_MIN` |
| `network-error` / `provider-###` / `provider-rejected` | ฝั่งผู้ให้บริการมีปัญหา |

ยอมให้ยอดคลาดเคลื่อนได้ 1 บาทเพื่อกันเรื่องเศษสตางค์กับค่าธรรมเนียม
ส่วนเลขบัญชีเทียบแค่ 4 หลักท้าย เพราะสลิปกับ API ปิดเลขกลางไม่เหมือนกัน
ปลายทางใบเดียวมักมีหลายเลข (เลขบัญชีธนาคาร + พร็อกซีพร้อมเพย์) จึงเทียบให้ครบทุกอัน
ตรงอันไหนก็ถือว่าตรง ถ้าข้อมูลไม่พอเทียบเลยจะปล่อยผ่านพร้อมติด `reason: "account-unchecked"`
ไม่ปัดตกสลิปที่ถูกต้อง

## เกณฑ์ตอนอนุมัติใบให้เอง

ตรงนี้เข้มกว่าการ "ตรวจแล้วตอบผลกลับ" หนึ่งระดับ เพราะไม่มีคนดูอยู่
ทุกข้อต้องผ่านครบถึงจะพลิกใบเป็น `approved`

| เช็คอะไร | เทียบกับอะไร |
| --- | --- |
| ใบยังรอตรวจอยู่ | `status == "pending"` ในใบ |
| ยอดตรง | ยอดในใบ (ไม่ใช่ `expectAmount` จากเบราว์เซอร์) ต่างได้ไม่เกิน 1 บาท |
| ปลายทางถูกบัญชี | `donate.promptPayId` ของช่องใน Firestore (ไม่ใช่ `expectAccount`) |

ข้อ 3 คือข้อที่ขาดไม่ได้ ถ้าเชื่อ `expectAccount` ที่เบราว์เซอร์ส่งมา
คนโอนจะ**โอนเข้าบัญชีตัวเอง**ให้ยอดตรงกับใบ แล้วบอก Worker ว่าปลายทางคือบัญชีตัวเองก็ได้
สลิปจริงทุกอย่าง ผ่านการตรวจกับธนาคารจริง แต่เงินไม่เคยไปถึงเจ้าของช่อง
— ใบยังขึ้นจอสตรีมพร้อมยอดเต็มและไปบวกเงินรางวัลทัวร์ด้วย

| `approveNote` | แปลว่า |
| --- | --- |
| `approved` | อนุมัติให้แล้ว |
| `no-bot` | ยังไม่ได้ตั้ง `BOT_EMAIL` / `BOT_PASSWORD` / `FIREBASE_API_KEY` / `FIREBASE_PROJECT` |
| `no-target` | เว็บไม่ได้ส่ง `channelId` / `donationId` มา |
| `donation-not-found` / `not-pending` | ใบหายไปแล้ว หรือมีคนกดอนุมัติ/ปฏิเสธไปก่อน |
| `amount-mismatch` | ยอดในสลิปไม่ตรงกับยอดในใบ |
| `account-mismatch` | เงินไม่ได้เข้าบัญชีพร้อมเพย์ของช่องนี้ |
| `account-unconfirmed` | ผู้ให้บริการไม่ส่งเลขปลายทางกลับมา เลยยืนยันไม่ได้ |
| `channel-has-no-account` | ช่องยังไม่ได้ใส่เลขพร้อมเพย์ จึงไม่มีอะไรให้เทียบ |
| `write-failed-###` | เขียน Firestore ไม่ผ่าน (uid ของบอทยังไม่อยู่ใน `admins` หรือกติกาไม่ให้) |

สามอันท้ายไม่ใช่ความผิดพลาด — ใบยังอยู่ครบในสถานะ `pending`
แค่ตกไปให้เจ้าของช่องกดอนุมัติเองเหมือนตอนไม่มี Worker

## รับคำขอเพลงจากแชทไลฟ์ (`?ingest=1`)

Worker ตัวนี้ยังเป็นทางเข้าของคำขอเพลงที่มาจากแชท TikTok ด้วย
โค้ดอยู่แยกไฟล์ที่ `song-ingest.js` และ deploy ไปพร้อมกันเอง

ทำไมต้องผ่าน Worker ไม่ให้สะพานเขียน Firestore ตรงๆ: สะพานรันบนเครื่องผู้ใช้
ซึ่งใครก็เขียนตัวเลียนแบบยิงเข้ามาได้ ถ้าให้มันเขียนเองก็เท่ากับเปิดให้ยัดเพลง
เข้าคิวช่องไหนก็ได้ในนามคนดูปลอม ตัวกลางจึงเป็นคนถือกุญแจ ตรวจกติกา แล้วค่อยเขียน

```http
POST /?ingest=1
Authorization: Bearer <INGEST_TOKEN>
```

| ฟิลด์ | จำเป็น | ความหมาย |
| --- | --- | --- |
| `channelId` หรือ `handle` | ✓ | ช่องปลายทาง ใส่ได้ทั้งไอดีเอกสารและ handle |
| `user.id` | ✓ | ชื่อผู้ใช้บนแพลตฟอร์มนั้น (ไม่ต้องมี `@`) |
| `user.name` | | ชื่อที่จะโชว์ในคิว ไม่ใส่ก็ใช้ `user.id` |
| `query` | ✓* | คำขอที่ตัดคำสั่งออกแล้ว — ชื่อเพลงหรือลิงก์ |
| `text` | ✓* | บรรทัดแชทดิบ Worker ตัดคำสั่งให้เอง และเมินบรรทัดที่ไม่ใช่คำขอเพลง |
| `platform` | | `tiktok` (ค่าเริ่มต้น) · `youtube` · `twitch` |

\* ต้องมีอย่างใดอย่างหนึ่ง — `query` สำหรับสะพานที่ตัดคำสั่งมาแล้ว
`text` สำหรับ webhook ของเครื่องมืออื่นที่ส่งบรรทัดแชทมาทั้งดุ้น

ตอบกลับเป็น `{ ok: true, id, videoId, title, author, position }`
หรือ `{ ok: false, reason }` ตามตาราง

| `reason` | แปลว่า |
| --- | --- |
| `ingest-disabled` / `bad-token` | ยังไม่ได้ตั้ง `INGEST_TOKEN` หรือส่งมาไม่ตรง |
| `not-a-command` | บรรทัดแชทธรรมดา ไม่ได้ขอเพลง (ไม่ใช่ความผิดพลาด) |
| `channel-not-found` / `songs-closed` | ช่องไม่มีอยู่ หรือปิดรับคำขอเพลงอยู่ |
| `no-match` / `video-not-found` | ค้นไม่เจอ หรือคลิปตามลิงก์เปิดไม่ได้ |
| `no-youtube-key` / `youtube-quota` | ค้นด้วยชื่อเพลงไม่ได้ (วางลิงก์ยังใช้ได้อยู่) |
| `duplicate` / `too-many` / `queue-full` | ติดกติกาของช่อง — ตัวเดียวกับที่หน้าเว็บใช้ |
| `cooldown` / `rate-limited` | ยิงถี่เกิน `MAX_INGEST_PER_USER_MIN` / `MAX_INGEST_PER_MIN` |
| `no-bot` / `bot-login-failed` | ยังไม่ได้ตั้งบัญชีบอท (ตัวเดียวกับที่ใช้อนุมัติสลิป) |
| `write-failed-403` | uid บอทไม่ได้อยู่ใน `admins` หรือยังไม่ได้ publish `firestore.rules` ตัวใหม่ |

**ใบที่เขียนจะมี `byUid` เป็น `tiktok:<ชื่อผู้ใช้>` และ `source: "tiktok"`**
รูปแบบ `byUid` ไม่ใช่เรื่องความสวยงาม — `firestore.rules` บังคับไว้ว่าบอทเขียนใบ
แทนคนอื่นได้เฉพาะเมื่อ `byUid` ติดป้ายแพลตฟอร์ม จะได้ชนกับ uid จริงของใครไม่ได้
(uid ของ Firebase ไม่มี `:`) และเพดาน "กี่เพลงต่อคน" ยังนับแยกรายคนได้เหมือนเดิม

**เรื่องโควตา** การค้นด้วยชื่อเพลงกิน YouTube Data API ครั้งละ 100 หน่วย
จากโควตาฟรี 10,000 หน่วย/วัน = ราววันละ 100 ครั้ง ซึ่งน้อยมากสำหรับแชทไลฟ์
Worker จึงแคชผลค้นหาไว้ (12 ชม.) และผูก KV ชื่อ `SONG_CACHE` เพิ่มได้
เพื่อให้แคชอยู่ข้าม instance — ส่วนคำขอที่วางลิงก์มาใช้ oEmbed ซึ่งไม่มีโควตาเลย

วิธีตั้งค่าฝั่งเครื่องสตรีมเมอร์อยู่ที่ [../bridge/README.md](../bridge/README.md)

## เพิ่มผู้ให้บริการเจ้าใหม่

แก้แค่ตาราง `ADAPTERS` ที่หัวไฟล์ `slip-verify.js`
เพิ่ม key ใหม่ที่มีฟังก์ชัน `request(payload, env)` คืน `{ url, init }`
ส่วนการอ่านผลลัพธ์ใช้ตัวแกะกลางร่วมกันอยู่แล้ว ถ้าเจ้าใหม่ใช้ชื่อฟิลด์แปลกๆ
ค่อยไปเติม path ในลิสต์ `AMOUNT_PATHS` / `DATE_PATHS` / `BANK_PATHS` ฯลฯ

> **อย่าลืม** endpoint และรูปแบบข้อมูลของทุกเจ้าเปลี่ยนได้ตลอด
> ที่เขียนไว้ในไฟล์อ้างอิงจากเอกสาร ณ ก.ค. 2026
> ถ้าตรวจแล้วขึ้น `provider-404` หรือ `no-amount` บ่อยๆ ให้ไปเทียบเอกสารล่าสุดก่อน

## แก้ปัญหาที่เจอบ่อย

| อาการ | สาเหตุที่น่าจะเป็น |
| --- | --- |
| เว็บขึ้นว่าตรวจไม่สำเร็จทุกใบ | ยังไม่ได้ `wrangler secret put API_KEY` หรือ `PROVIDER` สะกดผิด |
| เบราว์เซอร์บอกโดน CORS บล็อก | `ALLOWED_ORIGIN` ไม่ตรงกับโดเมนจริง (ระวัง `/` เกินท้าย และ http vs https) |
| ได้ `no-amount` ตลอด | ผู้ให้บริการเปลี่ยนชื่อฟิลด์ ดู `raw` ในใบโดเนทแล้วเติม path ในไฟล์ |
| `provider-401` | คีย์ผิด หมดอายุ หรือใส่คีย์ของคนละเจ้า |
| `provider-403` เฉพาะ SlipOK | ยังไม่ได้ตั้ง `BRANCH_ID` หรือใส่ผิดสาขา |

ดูล็อกสดตอนกำลังทดสอบ

```bash
wrangler tail
```
